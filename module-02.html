Mental models

Four words carry most of this guide: model, agent, harness and context. Get these straight now and every later module will make sense faster.

20 minutes Nothing to install

Think of it as an agency

You already know how an agency turns a client request into finished work. The same structure applies here, so we'll borrow it.

Model
A brilliant freelancer with no memory of your account
The model is the thing that reads and writes. Claude is a model. It is very capable and knows a great deal, but it starts every conversation knowing nothing about you, your client or yesterday's work.
Agent
That freelancer with a laptop and a task
An agent is a model that can take actions: read your files, run commands, edit code, search the web. It works in a loop until the task is finished. Claude Code is an agent.
Harness
The agency around them
The harness is everything you set up so agents do good work without you watching: written instructions, defined roles, a review step, rules about what needs your sign-off. You build this. It is the main subject of Phase 4.
Context
What is on their desk right now
Context is everything the agent can see in the current session: your messages, the files it has opened, the results of commands. The desk has a fixed size. When it fills up, older material falls off.

Chat answers. An agent acts.

In a chat window, you ask and it replies. You do the rest. An agent keeps going. It repeats four steps until the job is done or it gets stuck.

1. Read
Looks at your request and the files in the project.
2. Plan
Decides what to change and in what order.
3. Act
Edits files and runs commands on your computer.
4. Check
Runs the thing, reads the result, and goes back to step 1 if it's wrong.

Step 3 is the reason this guide spends time on permissions and approval rules. An agent that can act can also act wrongly.

What a harness is

The agent forgets. Files remember.

This is the idea most beginners miss. When you close a session, the agent's desk is cleared. Tomorrow's session starts from nothing. Long sessions have a related problem: the desk fills, and early instructions get pushed off.

The fix is to write things down in files the agent reads at the start of every session. The most important one is called the runbook. In Claude Code it is a plain text file named CLAUDE.md that sits in your project folder. Other tools read a file named AGENTS.md, and Module 18 shows how to keep one file that serves both.

A first runbook can be this short:

# Campaign brief generator
 
## What this is
A web app that turns a client intake form into a first-draft brief.
 
## Commands
Run locally: npm run dev
Run tests: npm test
 
## Rules
- Explain what you're about to do before you change files.
- Never put passwords or API keys in code.
- Nothing is done until you have run it and seen it work.

A mature one says much more. These lines come from the runbook behind this guide:

Read before asserting. If you haven't opened it, say you haven't opened it.
Root cause, not suppression. A change that makes a symptom disappear without explaining the mechanism is not a fix.
Uncertainty gets reported, not smoothed. Confidence is a claim, and claims get checked.

Notice that none of those lines are about code. They are about how to work. You are qualified to write rules like that today.

The parts of a harness

You will build each of these in Phase 4. For now, learn the names and what each one is for.

Runbook
The standing instructions for a project: what it is, how to run it, what is intentional, what is forbidden.
CLAUDE.md, AGENTS.md
Agents with roles
Separate specialists, each with its own instructions. One plans, one builds, one reviews, one hunts bugs, one writes the documentation.
architect, developer, quality-reviewer, debugger, technical-writer
Skills
Written procedures for things you do repeatedly, such as an end-of-session routine that saves where you left off.
session-wrap
Hooks
Small scripts that run automatically at set moments, such as a health check each time a session starts or a guard that blocks a risky command.
session start, before a command, session end
Connections
The ways an agent reaches other tools: your email, a spreadsheet, a database, a hosting service.
MCP servers, command-line tools
Gates
Your rules for what an agent may do alone and what must wait for your yes.
permissions, approval tiers

Why agents fail, and what fixes it

Almost every bad result traces back to one of five causes. Each has a fix you control.

What goes wrong
What it looks like
The fix
Vague brief
It builds something reasonable that is not what you wanted.
Say what done looks like. Start the sentence with "I can…", as in "I can paste a client URL and get a brief back."
Overloaded context
Late in a long session it forgets earlier decisions or repeats old mistakes.
End the session at a natural stopping point, save a short handoff note, and start a fresh one.
Confident and wrong
It states how something works without having looked.
A runbook rule to read before asserting, plus a second agent that reviews the first one's work.
Quietly wrong
Nothing crashes, but the output is subtly off, or a scheduled job stopped days ago and nobody noticed.
Make failures loud. Anything that runs unattended must tell you when it breaks.
Does too much
You asked for one fix and it rewrote three files to its own taste.
Scope rules in the runbook, and gates on anything with consequences.

Your job: approve consequences, not code

You do not need to read every line an agent writes. You do need to decide which actions are allowed without you. Three questions sort almost everything:

1
Does it cost money? A paid service, credits, a subscription.
2
Does it reach a real person? An email, a post, a message to a client.
3
Can it be undone? Deleting data and overwriting history cannot.

If the answer to any of them is yes, the agent stops and asks. Everything else it can do, then report. As a beginner you will keep Claude Code's default setting, which asks before most actions. Loosening that comes later, once you have the safeguards from Phase 4 in place.

Words you'll see again

session
One continuous conversation with an agent, from start to close.
repo
Short for repository. A project folder whose history is tracked, so any change can be reversed.
subagent
An agent started by another agent to do one piece of work and report back.
deploy
To publish your app so other people can use it on the internet.
handoff
A short note written at the end of a session so the next one can pick up where it stopped.
