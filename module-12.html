Inngest

Work that happens without a click: scheduled jobs and multi-step tasks that retry themselves and tell you when they fail.

60 minutesFree

What it is

Everything your app does so far happens because someone clicked. Some work should not wait for a click, and some should not make the person wait: a weekly summary, processing a large upload, a slow call to an AI model, retrying something that failed.

That kind of work is called a background job. Inngest is a service for running them. You describe the job as a series of steps. Inngest runs the steps in order, remembers which ones finished, and retries a failed step without repeating the ones before it.

Cost: The Free plan is $0 with no credit card and includes 50,000 runs a month. You can also do this whole module on your laptop without an account. See the pricing page.

Three words

Word
Meaning
event
A message saying something happened, such as an idea being created. Events can start jobs.
function
The job itself: the code that runs in response to an event or on a schedule.
step
One checkpoint inside a function. A finished step is saved and never runs twice.

What a job looks like

The weekly summary you are about to build has four steps.

Trigger
Monday, 8:00
A schedule starts the function. No person involved.
Step 1
Collect
Read each user's ideas from the last seven days.
Step 2
Summarize
Write one paragraph per user.
Step 3
Save
Store the summary so the app can show it.

If step 2 fails for one user, Inngest retries step 2. Step 1 does not run again.

Steps and retries

The question to ask about anything that runs unattended

A page that breaks gets noticed, because someone is looking at it. A job that breaks at 8:00 on a Monday gets noticed weeks later, if at all. Module 2 called this failing quietly.

From the runbook behind this guide
Anything scheduled or background has an observable failure mode. If it can die silently, it isn't finished.

So before you call the job done, answer one question: how will I find out that Monday's run failed? Inngest's dashboard lists failed runs, and you can have it notify you. Set that up, then write the answer into your agent instructions.

Type this to Claude
Add this rule to the project's agent instructions:
Every scheduled or background job must report failures somewhere I will see them. State where.

Steps must be safe to repeat

Retries mean a step can run more than once. A step that saves this week's summary is fine to repeat. A step that sends an email is not, unless it first checks whether the email already went out.

The word for safe to repeat is idempotent. You do not need to write that code. You need to ask the agent, for each step that reaches the outside world: what happens if this runs twice?

When you do not need it

Vercel has a basic scheduler of its own that can call one function on a timer. For a single, quick, once-a-day task, that is enough. Reach for Inngest when a job has several steps, needs retries, has to wait, or takes longer than a web request is allowed to.
