Phase 5: Capstone / Module 21

Build and ship

One real tool, built with the full stack and the full harness, live on the internet, with the paper trail to show you directed it.

About two weeksPennies of API credit

The assignment

Build one real tool, for a real person, and put it on the internet. You count as a real person. Use everything: the stack from Phase 3 and the harness from Phase 4.

In Module 1 you wrote down a repetitive task you wished a tool handled. In Module 2 you rewrote it as a sentence starting with I can. That sentence is your capstone, unless you have a better one now.

The rule for this module
A small tool that is finished beats a platform that is not.

If you need an idea

Four that fit the stack and the field. Shrink whichever you pick.

Idea 1
Brief builder
A client fills in a short intake form. A pipeline turns it into a structured first-draft brief. Briefs are saved per client, and a weekly job lists the ones still waiting for review.
I can paste a client's answers and get a brief I would only need to edit.
Idea 2
Performance digest
Upload the weekly export from an ad platform. The app stores it, compares it with last week, and writes a plain-language summary of what changed.
I can upload a file on Monday and read what moved and why it might have.
Idea 3
Competitor watch
Keep a list of public pages to watch. A scheduled job checks them, notes what changed, and sends a short digest only when something did.
I can add a page and hear about it only when it changes.
Idea 4
Pitch board
Enter a campaign idea. Get back a board of taglines and concept images, saved per idea, with a record of which model made each asset.
I can type an idea and have a board to react to in two minutes.

Idea 3 reads other people's websites. Watch only public pages, check each site's terms, and keep the schedule slow.

What it must have

This is the checklist. It is also what a reviewer, human or agent, will look for.

The product
It works, and it is safe
A live address. Sign-in. Each user sees only their own data, proven with two accounts. At least two database tables. One scheduled or background job that reports failure somewhere you will see. One model call that returns structured fields and is checked. No secret anywhere in the repository.
The harness
Agents can work on it
AGENTS.md with cited lines and a Gates section. CLAUDE.md importing it. A planner and a reviewer that you used. At least one skill and one hook. HANDOFF.md, STATUS.md and DECISIONS.md kept current.
The process
You directed it
A scope document. A plan whose acceptance lines start with I can. At least one feature taken through a worktree, a single review and a preview you tested. An undo command written before each merge. A live check recorded after.

Seven stages

Each has a prompt to start it and a file that comes out of it.

1
Decide what done means

Write three to five sentences that start with I can. They are the whole product. If a feature does not serve one of them, it is not in this version.

Example, for the brief builder
I can sign in and see only my own clients.
I can paste intake answers and get a structured brief back within a minute.
I can edit a brief and my changes are still there tomorrow.
I can see, every Monday, which briefs are still waiting for review.
2
Scope it
Type this to Claude
Interview me to scope this project. Ask one question at a time, ten at most.
Then write SCOPE.md with: what it is, who it is for, the I can lines, what is in this version,
what is explicitly out, constraints, and the three biggest risks.

Read SCOPE.md. Cut something. Then cut something else.

3
Plan it
Type this to Claude
Use the planner. Break SCOPE.md into separate pieces of work in PLAN.md.
Each piece has its own acceptance lines, the files it touches, and what it depends on.
The first piece is the smallest thing that can be live: one page, deployed, behind sign-in.
Mark which pieces could be built at the same time.
4
Set up the harness before the code

Create the project and the repository, then copy in the starter kit and fill in the brackets. Do this first. An agent that starts with a runbook makes fewer messes than one that gets a runbook later.

5
Get to live on day one

Build the first piece from the plan and deploy it. It will do almost nothing. That is the point. Every problem with accounts, keys and deployment surfaces now, while the app is too small for anything else to be wrong.

6
Build piece by piece

One piece at a time, each through the pipeline from Module 20.

Type this to Claude
Build piece [number] from PLAN.md in a worktree. Run all tests. Have the reviewer review it once and fix only must-fix findings.
Write the undo command into HANDOFF.md, push the branch and give me the preview address. Do not merge.

Test the preview against that piece's I can lines yourself. Merge. Check it live. Update STATUS.md. Run /session-wrap. Start a fresh session for the next piece.

7
Harden it

Before you call it finished, try to break it.

Test
How
Data isolation
Sign up as a second user. You should see nothing belonging to the first.
Failure reporting
Have the agent make the background job fail once. Confirm you were told.
Secrets
Ask the reviewer to search the whole repository history for anything that looks like a key.
A stranger
Hand it to someone who has never seen it. Say nothing. Watch where they get stuck.

Keep it small

If you are tempted to
Do this instead
Add a feature that no I can line needs
Write it in STATUS.md under Next, and leave it there.
Support every case
Support the one you have. Note the others as out of scope.
Polish the design before it works
Get every I can line passing first. Then use a design pass.
Build tools for the agents
Stop. Finish, don't fill.
Start over because it got messy
Ask the agent what it would simplify, and do that.

A reasonable size is two weeks of evenings. If your plan has more than six pieces, it is too big.

When you are stuck

Kind of stuck
First move
An error message
Paste the whole thing to the agent. Then check the troubleshooting table in the module for that tool.
The agent keeps failing at the same thing
Start a fresh session with the handoff. If it fails again, the plan for that piece is wrong. Go back to the planner.
You do not understand what it built
Ask it to explain the piece to someone who has never coded. Do not approve what you cannot follow.
You do not know what to do next
Read STATUS.md. If it does not tell you, that is the first thing to fix.

What to hand in

Item
What it shows
The live address, with a test account
It works.
Access to the private repository
How it was built, including the runbook and its history.
README.md
What it does, the I can lines, and what you would do next.
DECISIONS.md
The calls the agents made, and that you knew about them.
A two-minute demo recording
Each I can line, done on screen.
A one-page retrospective
What the agents got wrong, which runbook lines you added because of it, and what you would do differently.

The retrospective is the part to spend time on. Anyone can end up with a working app. Being able to say why each rule in your runbook exists is what shows you were directing.

For the instructor: one way to assess it

Four questions, each answerable from what is handed in. Weights are yours to set.

Question
Evidence
Strong work looks like
Does it work?
The live address and the demo.
Every I can line passes, done by someone other than the builder.
Is it safe?
The two-account test, the repository history, the Gates section.
No cross-user data, no secrets in history, and a clear list of what waits for a human.
Could someone else pick it up?
AGENTS.md, HANDOFF.md, STATUS.md.
A fresh agent session can state the project's rules and resume work from the notes alone.
Did the student direct it?
SCOPE.md, PLAN.md, DECISIONS.md, the retrospective.
Scope was cut on purpose, decisions are logged, and runbook lines trace back to specific mistakes.

After this

You started this guide asking a chatbot questions. You are finishing it with a live product, a team of agents that can extend it, and a written set of rules for how they work. The tools will change. Several named in this guide will be replaced within a couple of years.

What stays is the part you practiced most: saying what done looks like, deciding what needs your yes, and checking the result yourself. That was the job in Module 1, and it still is.
