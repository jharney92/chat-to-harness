Secrets and API keys

Passwords for programs. Learn where they live and where they must never go, before you have one worth stealing.

40 minutesFree

What a secret is

A secret is a password meant for programs instead of people. An API key, a database address with its password, an access token. Whoever holds one can act as you with that service: read your data, send messages in your name, spend your money.

Leaking one is the most common serious mistake beginners make, and it takes seconds. This module comes before the database for that reason. Learn the habit while the stakes are zero.

Names in code, values somewhere else

Every tool in this guide follows the same pattern.

In your code, and on GitHub
The name
process.env.DATABASE_URL
Safe for anyone to read. It says which secret is needed, not what it is.
In .env.local, and in Vercel
The value
DATABASE_URL=postgres://user:pass@host/db
Never leaves these two places. Not in code, not in Git, not in a chat.

Five rules

Rule
Why
Never type a secret into a code file.
Code gets committed, and commits get pushed.
Never commit a file whose name starts with .env.
That is where the values live. Your project's .gitignore already excludes them. Check that it does.
Never paste a secret into a chat, a screenshot or a message.
That includes a chat with an AI. Put the value in the file yourself.
Anything named NEXT_PUBLIC_ is public.
Next.js copies those values into the code every visitor's browser downloads. Use that prefix only for values that are meant to be seen.
One key per project.
When one leaks, you replace that one and nothing else breaks.

Practice with a harmless value

2
Create the file yourself
Type this
touch .env.local
open -e .env.local

A text editor opens. Type this line, save and close.

In the file
GREETING=Hello from the server
3
Use it by name
Type this to Claude
Show the GREETING environment variable under the page title.
Read it on the server. Do not print its value anywhere else.

Stop and restart npm run dev, then refresh. Your greeting appears.

4
Prove it is not in Git
Type this
git status
You should see: the files the agent changed, and no mention of .env.local.
5
Push, and watch production miss it
Type this to Claude
Commit and push.

Open your live site when the deployment is Ready. The greeting is blank. The value exists on your laptop only. This is the single most common reason an app works locally and fails live.

6
Give the value to Vercel
Type this
vercel env add GREETING

Enter the value when asked and apply it to every environment. A new variable only takes effect on the next deployment, so redeploy.

Type this to Claude
Redeploy production.
You should see: the greeting on your live site.
7
Pull values down when you need them
Type this
vercel env pull .env.local

This copies the project's development values from Vercel into your local file. It is how you set up the same project on a second computer.

Agents and secrets

An agent working in your folder can read .env.local. That is expected, and it is how the agent runs your app. What you control is what it does with the values.

From the runbook behind this guide
Secrets are referenced by name and piped, never echoed, logged, printed, or committed.
Type this to Claude
Add this rule to the project's agent instructions:
Refer to secrets by name only. Never print, log or commit their values.

If one gets out

Replace it first. Clean up second.
Go to the service that issued the key and revoke or regenerate it. Do this before anything else. Deleting the file or the message does not help: a committed secret stays in the repository's history, and you have to assume it was copied.

Then put the new value in .env.local and in Vercel, redeploy, and ask the agent to remove the file from Git tracking without deleting it from your computer.

GitHub blocks pushes that contain recognizable keys, but by default only for public repositories. Your private ones do not get that check, so the habit is the protection.
