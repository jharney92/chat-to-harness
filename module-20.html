Phase 4: The harness / Module 20

Running the factory

Decide what agents may do without you, run a feature through a full build pipeline, and learn what keeps an unattended system finishing work instead of making it.

2 to 3 hoursFree

From watching every step to checking the result

You now have a runbook, a small team of agents, a few skills and a guard. Until this point you have approved every action. This module is about stepping back safely, so that work continues while you are doing something else.

Anthropic's guidance reduces the question to four checks. Before you leave an agent alone, you should be able to answer each.

Question
What answers it
Does it know what done looks like?
Acceptance criteria that start with I can.
Can it check its own work?
Tests, and a separate reviewer.
What is it allowed to touch?
Gates, permission rules, and a separate copy of the project to work in.
What stops it?
A spending limit, a context limit, and one review instead of endless ones.

The rest of this module takes them in turn, using the rules from the setup behind this guide.

Gates: approve consequences, not code

In Module 2 this was three questions. In practice it grows into four tiers. Every action an agent might take falls into one.

Tier 1
Just do it. Tell me after.
Internal, reversible changes that passed review and tests and have a way back.
Reported in a daily summary.
Tier 2
Do it, with a veto window.
Anything you or others would notice: alerts, schedules, new sources of data.
One line: doing this at 3:00 unless you say stop.
Tier 3
A real gate. Nothing moves.
Money beyond the agreed cap. Anything that reaches a real person. Anything irreversible. Access and credentials. What a customer is promised or pays.
Waits for an explicit yes.
Tier 4
Decide, and flag it.
Every other judgment call: a threshold, a default, the order of work.
The agent picks, ships, and logs the choice so you can revisit it.

Tier 4 is what makes it move

Without it, an agent stops to ask about everything, and you become the bottleneck. With it, the only things that wait for you are the ones in tier 3.

From the runbook behind this guide
Never block a piece of work waiting on such a call.

When something does need you, it should arrive ready to decide. The real setup requires each request to be a card with the same contents.

What a decision request must contain
The full ask
The context needed to answer it
Every option, each with: cost, who will see it, how to undo it
My pick, and why
What happens if you do not answer

A standing allowance

Some tier 3 items come up so often that asking each time defeats the purpose. The answer is a pre-approved allowance, written into the runbook, with hard numbers.

From the real runbook, shortened
Money: API spend up to 10 dollars per run and 25 dollars per day across all projects. Over a cap = ask.
Unchanged, always a real gate: any send or outbound message; other people's records;
credentials, permissions and access; money beyond the caps; pricing and contracts.

Yours will have smaller numbers. The shape is what matters: a limit the agent can check itself against, and a list of things no allowance covers.

About the setup this guide comes from
It runs with permissions bypassed, on a dedicated machine that does nothing else, behind every safeguard described in this phase: tiers, hooks, a scanner that blocks secrets from being committed, and an independent review of every change. The build pipeline

Every feature in the real setup goes through the same six steps.

1
Scope
A plan with acceptance criteria.
2
Build
In a separate copy of the project. The builder runs every test before asking for review.
3
Review
Once, by an agent that did not build it.
4
Fix
Only what the reviewer marked as must-fix.
5
Merge
When tests are green and the undo command is written down.
6
Check live
Someone uses the feature on the real product.

Two rules inside it

From the runbook behind this guide
Nothing is done until it's been exercised, not just built.

Merged is not finished. In the real setup a piece of work that has been merged but not checked on the live product is marked built, and it may stay that way for 24 hours at most. After that it is treated as a defect. Done means a person, or an agent acting as one, used the feature where customers would.

From the runbook behind this guide
One review, then ship.

Review can loop forever: fix, re-review, new nitpick, fix again. The rule is one review. Must-fix items are fixed and the tests rerun. Smaller suggestions are fixed if they take a few minutes and otherwise noted for later. The fix itself is not reviewed again unless it touched something that sends, spends or deletes.

Parallel work without collisions

Two agents editing the same folder will overwrite each other. Git has a feature called a worktree: a second copy of the project in its own folder, on its own branch, sharing the same history. Each agent gets one.

Type this
claude --worktree add-tags
From the runbook behind this guide
Parallel work: a worktree, never a second session in the same folder.

What things cost, and why

The instinct is to save money by using a cheaper model. The setup behind this guide measured it and found something else.

From the runbook behind this guide
Route models by the cost of a mistake. Put the cost guard on loops, not the model.

The expensive thing was one long session. Each new message makes the agent reread everything before it, so a conversation that runs for days pays for its whole history on every turn. One such session used half of two weeks' allowance.

Rule
Why
One session per stage of work. End around 60% of the context, write a handoff, start fresh.
A short session rereads little.
Keep verification out of the main session.
Running all the tests or reading long logs goes to a subagent that returns a verdict, not the output.
Fast model for finding and reading. Mid model for building from a plan. Strongest for planning and for reviewing anything risky.
Spend where a mistake would hurt.
Check usage before starting a large batch.
Near the limit, finish what is open and stop.

The orchestrator

At the top of the real setup sits one session whose job is to never build anything.

From the runbook behind this guide
Orchestrate, decide, delegate. Never build in the main context.

It reads a state file when it starts, hands each piece of work to a fresh session or a subagent, reads the results, and updates the file. When its own context fills, it writes the state down, ends, and a new one takes over from the file.

The four sections of its state file
In flight
Waiting on me
Sessions running
Next

Everything that needs a human collects in one list. The instruction that created it:

From the runbook behind this guide
You do all the work you can without me, then hit me each day with a decision desk link.

Finish, don't fill

One lesson from running this is worth more than the rest. Given spare capacity and told to stay busy, agents build infrastructure. They improve their own tools, add dashboards and propose new projects, while the products stay unfinished. It looks like progress.

From the runbook behind this guide
Measure finished outcomes, never usage.

The corrected rule sends idle capacity, in order, to known defects in things you use, then to getting each product to the point where it can be demonstrated, then to verifying work that is built but not checked. Nothing new unless you ask or something is broken.

Run one feature through your pipeline

1
Write your gates into the runbook
Type this to Claude
Add a Gates section to AGENTS.md with four tiers.
Tier 1, do and report: edits on a branch, running tests, reading anything.
Tier 2, tell me first: changing a schedule or adding a new outside service.
Tier 3, wait for my yes: merging to main, spending over 2 dollars in a run, sending anything to a real person, deleting data, changing keys.
Tier 4, decide and log it in DECISIONS.md: everything else.
2
Loosen one notch, and add rules
Type this to Claude
Set this project's default permission mode to accept edits. Always allow running tests, the build, and read-only git commands.
Always deny forced pushes and rm -rf. Read the current permissions documentation first and show me the file.
3
Commit, then start in a worktree
Type this
cd ~/Code/campaign-notes
git status
claude --worktree add-tags
4
Hand over the feature
Type this to Claude
Feature: tags on ideas. Use the planner to write a plan with acceptance criteria that start with I can. Show me the plan and wait.
After my OK: build it, run all tests, have the reviewer review it once, fix only must-fix findings,
write the exact command that would undo the merge, push the branch and give me the preview address. Do not merge.
5
Do your part

Read the plan and say yes or no. When the preview address arrives, open it and try each I can line yourself. This is the check that cannot be delegated.

6
Merge and check live
Type this to Claude
Merge it. When the deployment is ready, confirm the feature works on the live address and update STATUS.md.
7
Wrap up
Type this to Claude
/session-wrap

Count what you did. You approved a plan, tested a preview and said merge. Three decisions, each about a consequence. That is the job.

Do not build the factory first

Everything in this phase was added to the real setup because something went wrong without it. Copying all of it on day one gives you the weight without the understanding.

Add this
When
A reviewer
Now. It is cheap and catches real problems.
A guard hook
The first time an agent runs something that frightens you.
Gate tiers
When you notice you are approving things without reading them.
Worktrees
The first time you want two things built at once.
An orchestrator
When you are running more sessions than you can keep track of.
Auto mode
When all of the above are in place and you trust them.
