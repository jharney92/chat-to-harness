The runbook

Rebuild the file your agents read at the start of every session, using a working one as the model.

75 minutesFree

Where you are

Since Module 6 you have had a runbook: a short file the agent reads at the start of every session. You have added rules to it one at a time, about secrets, tools, connected services and background jobs.

This module rebuilds it properly. The examples come from the working setup behind this guide, with names and private details removed. Read them as one person's answers after a couple of years of mistakes. Yours will be shorter, and should be.

Two names for one file

Claude Code reads a file named CLAUDE.md. Most other coding agents read one named AGENTS.md. You will end up using more than one agent, so write the instructions once, in AGENTS.md, and have CLAUDE.md point to it.

CLAUDE.md, the whole file
@AGENTS.md
 
(Anything below this line applies to Claude only.)

Your Next.js project already has an AGENTS.md, created in Module 7. Claude Code can read that file directly, and the one-line CLAUDE.md makes the arrangement explicit.

Every line costs attention

The runbook is loaded into every session, for every task. A line about database migrations is read when the agent is fixing a typo. Anthropic's guidance is to keep the file under about 200 lines, and says the work of maintaining one is mostly removing lines.

So the test for a line is not whether it is true. It is whether the agent would do something worse without it.

A project runbook, section by section

These excerpts are from a real web app on the same stack you have been using. It has five sections.

1. What it is, and what it is not
## What this repository is
- A private dashboard for reviewing drafted outreach and recording manual sends. <!-- README.md opening -->
- Next.js, React and TypeScript serve the app; Neon Postgres stores the data. <!-- README.md; migrations/ -->
- A separate system produces the drafts. This app does not generate or send emails. <!-- README.md opening -->
2. Commands
## Commands
- Run local app: npm run dev <!-- package.json scripts -->
- Build: npm run build <!-- package.json scripts -->
- Full unit suite: npm test <!-- package.json scripts.test -->
- Explicit schema migration: npm run migrate; inventory target and every pending file first. <!-- README.md Local setup -->
3. Where things live. Names of secrets, never values
## Topology, stores and env names
- The app listens on port 4310 in dev; Neon is the persistent store. <!-- package.json scripts -->
- DATABASE_URL selects the database; DESK_TOKEN is browser access. <!-- .env.example -->
- Migrations are explicit: neither startup nor build applies them. <!-- scripts/migrate.ts -->
4. What must stay true, and what is intentional
## Invariants and deliberate behavior
- Raw pasted email is stored for training but never returned through the API. <!-- README.md Dashboard workflow -->
- An empty published batch intentionally hides active items while preserving the archive. <!-- README.md API -->
- Tests use a mock database and do not prove the real one works. <!-- README.md Local setup -->
5. How it ships, and what never happens
## Deployment and prohibitions
- Production is git-connected: a push or merge to main IS the production deploy; never run a CLI deploy. <!-- README.md Deploying -->
- Never aim acceptance or destructive migration tests at production. <!-- test/postgres-test-pool.ts -->
- Never place token or database URL values in logs, commits or runbooks; document env names only. <!-- .env.example -->
- Never call a manual done record an automatic email send. <!-- README.md opening -->

Three habits that make a runbook trustworthy

Habit 1
Cite the source
Look at the end of every line above. Each names the file the fact came from. The agent can check it, you can check it, and a line with nothing to cite probably should not be there.
Habit 2
Say what is intentional
Agents fix things. Anything that looks like a bug but is deliberate needs a line saying so, or one day it will be helpfully repaired. The larger runbooks in this setup have a section titled Looks like a bug, is design.
Habit 3
Date your claims
A sentence like all tests pass is false the moment something changes. Write it as a receipt: the most recent recorded result, with its date, and a note that it is not a fresh count.

From the runbook behind this guide
This file is context, not enforcement. If something here is load-bearing enough that a violation would cost real money or data, it belongs in a hard gate too, not just here.

That last line matters. A runbook is advice. Agents follow it almost all the time. For the few things that must never happen, Module 19 adds hooks and Module 20 adds permission rules, which the agent cannot talk its way past.

Weak lines and strong lines

Instead of
Write
Write good, clean code.
Delete it. It changes nothing.
Be careful with the database.
Never run a migration that drops or renames a column without my yes.
Make sure things work.
Run npm test before saying a change is done. State the result.
Do not break production.
A push to main deploys. Do all work on a branch.
Keep me updated.
End every task with: what changed, how you checked it, what is left.

A strong line names an action and the condition that triggers it. If you cannot tell whether the agent followed a rule, the rule is too vague.

What does not belong in it

Leave out
Put it here instead
Secret values
.env.local and your host's settings. The runbook lists names only.
Today's status
A STATUS.md or HANDOFF.md file that changes every session.
Long step-by-step procedures
A skill, which loads only when needed. Module 19.
Anything the agent can see by reading the code
Nowhere. It will read the code.

Rebuild yours

1
Rewrite the project runbook
Type this to Claude
Read the whole project, then rewrite AGENTS.md with these five sections:
What this repository is, Commands, Topology and env names, Invariants and deliberate behavior, Deployment and prohibitions.
Keep every rule we have added so far. End each line with a comment naming the file it came from.
Leave out anything you cannot cite. Keep it under 80 lines.
Then make CLAUDE.md contain only the line @AGENTS.md.
2
Read every line

This is your file. Delete any line you do not understand or do not agree with. Ask the agent to explain any line before you keep it.

3
Write your global runbook

Have the agent create it, then edit it by hand until it sounds like you.

Type this to Claude
Create a global CLAUDE.md in the .claude folder in my home folder with these parts, and ask me questions to fill them in:
Context: who I am, what I am learning, how I like answers.
How to think: read before asserting; say when unsure; do not change what I did not ask about.
Quality bar: nothing is done until it has been run and seen to work.
Never: print or commit secrets; delete data without my yes; push to main without my yes.
Keep it under 30 lines.
4
Test it cold

Exit, start a new session, and ask.

Type this to Claude
What must you never do in this project, and where does each rule come from?
5
Commit it

The project runbook is part of the project. It belongs in Git like everything else, and its history is the history of what you learned.

How a runbook grows

Do not try to write the perfect file now. The real one quoted above was not written. It accumulated. Most of its lines carry a date, because each was added the day something went wrong.

When
Do this
The agent makes the same mistake twice
Add one line that would have prevented it.
You correct the agent's tone or format twice
Add it to the global file.
A line has not mattered in a month
Delete it.
A rule keeps being broken despite the line
It needs enforcement, not better wording. Module 19.
