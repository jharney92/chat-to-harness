Agents, skills and hooks

Turn one assistant into a team with roles, give it procedures it can run on request, and add checks that happen whether anyone remembers or not.

2 hoursFree

Three ways to extend an agent

The runbook tells one agent how to behave. These three add specialists, procedures and automatic checks. Each is a plain text file.

Piece
What it is
Where it lives
Use it when
Subagent
A specialist with its own instructions and its own clean desk.
One file per agent in the agents folder inside .claude
A job needs a different role, or a lot of reading you do not want cluttering the main session.
Skill
A written procedure, loaded only when it is needed.
A SKILL.md file in its own folder inside the skills folder
You keep pasting the same instructions or checklist.
Hook
A script that runs by itself at a set moment.
A script file, registered in settings.json
Something must happen every time, or must never happen at all.

All three can live in a project's .claude folder, where they apply to that project and travel with it in Git, or in the .claude folder in your home folder, where they apply everywhere.

Subagents: a team instead of an assistant

A subagent runs in its own context. It does its work, reads what it needs to read, and hands back a short result. Three things follow from that.

Benefit
Why it matters
A clean desk
The subagent's forty files of reading never enter your main session. You get the conclusion.
Separation of duties
The agent that built something is the worst one to judge it. A reviewer that never saw the work being made reads it fresh.
The right model for the job
Searching and summarizing can go to a fast, inexpensive model. Planning and risky reviews go to the strongest.

The team behind this guide

Five roles handle almost all building work. Each one is a single file.

Plans
architect
Turns a vague request into a plan others can follow: decisions and the reasons for them, which files change, and how to tell it worked.
You design; others implement.
Builds
developer
Implements the plan, makes the smallest change that satisfies it, and runs the full test suite before reporting.
You execute; others design.
Checks
quality-reviewer
Reads the change looking for ways it could fail in real use. Returns one of two words: MERGE or FIX.
Find what others miss.
Investigates
debugger
Gathers evidence before forming any theory about a bug, reports the cause, and removes every trace of its investigation.
You diagnose; others fix.
Documents
technical-writer
Updates the runbook and comments after the code is finished, describing what exists and nothing else.
Every word must earn its place.

Two more, for people who care how things look

Visual
design-expert
An art director. Screenshots the current product, studies well-regarded sites for the same audience, proposes two or three directions, picks one with reasons, and delivers colors, type and spacing as values a builder can use.
A design system that hedges is not a design system.
Usability
ui-expert
A product designer. For each screen, writes the user's job in one line, counts the steps to do it, and finds where a person would hesitate or make a costly mistake.
Job, then screen.

What an agent file looks like

In the file
---
name: developer
description: Implements architect specs into working, tested code. Use when a plan
exists and the task is to write the implementation.
model: sonnet
---
You are an expert Developer who translates architectural specifications into
working code. You execute; others design.
 
Success means faithful implementation: code that is correct, readable, and
follows project standards.
Part
What it does
name
What you and other agents call it.
description
When to use it. The main agent reads this line to decide whether to hand a task over, so write it as a trigger.
model
Which model runs it. Optional.
Everything below the second dashed line
The role itself: who it is, what it does, what it must not do, and how to report.

Four patterns worth copying

Pattern
From the real files
State what the role does not do.
The architect writes what to change. It does not write the code. The debugger finds the cause. It never applies the fix.
Fix the output format.
The reviewer must answer in a set shape: verdict first, then each finding with its location, the problem, what would go wrong, and the fix.
Give it a way to say stuck.
Every agent has one format for raising a problem: blocked, needs a decision, or uncertain, with what it needs to continue.
Ask open questions, not yes or no.
The reviewer asks what happens when this fails, not can this fail. A yes-or-no question invites the answer the asker hoped for.

Build a reviewer

1
Have the agent write the file
Type this to Claude
Create a project subagent called reviewer in the agents folder inside .claude. It is read-only and never edits files.
It reviews a change for: database queries missing the owner filter, secrets in code or logs,

It must answer in this format: VERDICT: MERGE or FIX, then each finding with location, issue,

Type this to Claude
Create a project subagent called planner. It never writes code. Given a request, it explores the project and writes a plan:

The expert pattern

Two agents in this setup are experts in a single outside product each. They share a design worth knowing, because you can build one for any tool you rely on.

1
A knowledge base
The product's help articles saved as text files in a folder, with an index saying which file covers what.
2
A live connection
An MCP server for the product, so the agent can see how your account is set up.
3
Safety rules
Read freely. Confirm before any change, stating exactly what and how many.
From the runbook behind this guide
Read how the feature is supposed to behave. Inspect the actual configuration. The gap between the two is usually the diagnosis.

Skills: procedures that load on demand

A skill is a set of instructions for one kind of task. Unlike the runbook, its contents are not read every session. The agent sees only a one-line description until the skill is needed, so a long procedure costs almost nothing while idle.

Here is a real one, shortened. It runs at the end of a working session.

In the file
---
name: session-wrap
description: End-of-session routine. Run when I say "wrap up" or "done for today".
---
1. State check: anything half-done? Uncommitted changes? Unpushed commits?
Surface each with a recommendation. Don't silently leave them.
2. Memory: update the resume note so a fresh session could pick up cold from it.
Prefer updating the existing note over creating a near-duplicate.
3. Handoff: if work continues in a new session, write the handoff and commit it.
4. Sign-off: one short summary. What shipped, what's verified, what's pending on me.

You have been doing a manual version of this since Module 6. Now make it a skill.

Type this to Claude
Create a skill called session-wrap in the skills folder inside .claude in my home folder, so it works in every project.
Base it on the four steps above, using HANDOFF.md as the resume note.

From then on, typing /session-wrap runs it, and so does saying wrap up.

A pipeline made of skills

Larger builds in this setup pass through three skills in order. Each produces a document the next one reads.

Skill 1
Scope
An interview. What are you building, for whom, and what constrains it? Produces a short scope brief.
Skill 2
Architect
Breaks the brief into separate pieces of work, each with clear boundaries, so several can be built at once.
Skill 3
Sequence
Turns each piece into a ready-to-run prompt, and says which can run in parallel and in what order.

The prompts that come out the end all have the same parts. This shape is worth using even when you write a prompt by hand.

The parts of a build prompt
Goal
Why this piece exists
Context the agent needs, stated in full
Files likely to change
Steps, numbered
How to verify, numbered
Done when: (each line testable)
Out of scope
I can: (one line on what I can do on the live product afterwards)

Hooks: things that happen every time

A hook is a small script that Claude Code runs at a fixed moment. It needs no remembering and no cooperation from the agent.

Moment
Example use
When a session starts
Check that your services are healthy and tell the agent about anything broken.
When you send a message
Add a piece of context to it.
Before the agent runs a command or edits a file
Inspect it, and block it if it breaks a rule.
After a command or edit
Run a formatter or a quick check.
When a session ends
Tidy up or save state.

Three real hooks

On each message
The hype check
After 6 in the evening, or when a message contains words like stuck or broken, this hook quietly tells the agent to open its reply with an encouraging nickname. It is twenty lines long and exists purely for morale.
The best first hook is a harmless one.
Before a command
The search guard
Blocks one specific kind of file search that, on a Mac, freezes the session on an invisible permission prompt. The comment at the top records the two dates it happened before the hook was written.
Every guardrail has a scar.
On session start
The health check
Looks at scheduled jobs, backups, disk space and unsaved work, and reports only what is wrong. A healthy system produces no output at all.
A hook that blocks startup is worse than no hook.

Build a guard

1
Have the agent write it
Type this to Claude
Create a hook that runs before any terminal command and blocks it if it contains git push --force,
or rm -rf pointed anywhere outside this project folder. Read the current Claude Code hooks guide first.
Put the script in a hooks folder inside .claude, register it in the project's settings.json,
put a comment at the top saying why it exists, and make sure a mistake in the script cannot block every command.
2
Test it
Type this to Claude
Run git push --force.
You should see: the command refused, with your hook's message as the reason.
From Claude Code's documentation, paraphrased
A blocking hook stops the action before any permission rule is considered.

That is the difference from Module 18. A runbook line asks. A hook enforces. Put a rule in a hook when breaking it once would cost real money or data.

When something goes wrong

What you see
What it means
What to do
The agent never uses my subagent
Its description does not match how you phrase requests.
Rewrite the description as a trigger, or ask for the subagent by name.
A subagent edited files it should not have
It inherited every tool.
Limit its tools in the file. A reviewer needs to read, not write.
My skill does not appear when I type a slash
The file is in the wrong place or misnamed.
It must be a file called SKILL.md inside a folder named for the skill.
My hook does nothing
The script cannot be run, or it is not registered.
Ask Claude to check that it is executable and listed in settings.json.
Every command is now blocked
The hook has a bug and fails closed.
Remove its entry from settings.json, then fix the script.
