Building with AI, and building AI in

Until now, AI has been the builder. Claude Code wrote Campaign Notes, and the finished app contains no AI at all. Its weekly summary is assembled by ordinary code.

This module puts a model inside the app. When the summary job runs, your code will send the week's ideas to Claude and get a written summary back. The app itself becomes the one asking.

The way an app talks to a model is called an API. Your code sends text and receives text. You pay for what you use, measured in tokens, which are small pieces of words.

Agent or pipeline?

The most useful design decision in this guide. An agent chooses its own steps. A pipeline follows steps you chose.

Agent
You give a goal. It decides how.
Flexible, and good at open-ended work such as building software. Harder to predict, harder to test, and it can wander.
Claude Code is an agent.
Pipeline
You define the steps. A model does each one.
Each step is a single request with one narrow job. Predictable, testable and cheap. Right for work that repeats.
Your summary job is about to be a pipeline.

The person who wrote this guide runs both, and for anything that repeats in production he reaches for a pipeline first. An agent is the right tool for building the pipeline. It is often the wrong tool for being it.

What a real pipeline looks like

This is the shape of a production system that drafts outreach emails every night. No draft goes anywhere until a person approves it.

Step 1
Plan
One model picks the angle, using only facts that were verified earlier.
Step 2
Write
A second, cheaper model drafts from that plan and nothing else.
Step 3
Check
A stronger model compares the draft with the facts and flags anything unsupported.
Step 4
Gate
Plain code enforces rules: length, banned phrases, a clear ask.
Step 5
Review
A person reads it and decides.

Six lessons from running it

Lesson
What it means in practice
Use different models for different jobs.
A fast, inexpensive model writes. A stronger one checks. You are not obliged to use the best model everywhere.
Record what produced each output.
Save the model name and the prompt version with every result, so a week later you can tell why something changed.
A failed check does not delete the work.
The draft is kept and marked rough, with the reasons. A person can still use it or fix it.
A budget stop is not a failure.
Each run has a spending cap. When it is reached the run pauses and says so. Nothing is broken.
A busy provider is not a failure either.
If the model service is temporarily unavailable, that item waits for the next run. Only real errors raise an alarm.
Nothing reaches a real person without a click.
The pipeline prepares. A human sends.

Before adding a rule or check, remove or loosen one.

That last line is about a trap. Every bad output tempts you to add another rule. Stack enough of them and the model has no room to write well. Measure before and after.

Ask for data, not prose

Code cannot do much with a paragraph. It can do a great deal with labelled fields. Structured output means giving the model a template to fill in, called a schema, and getting back exactly that shape every time.

The shape you will ask for
summary one paragraph
themes up to three short phrases
strongest_idea the title of one idea from the list

Your page can then show the themes as tags and link the strongest idea, instead of displaying a block of text.

When something goes wrong

What you see
What it means
What to do
401, or invalid API key
The key is missing, mistyped or expired.
Check .env.local and Vercel. Create a new key if it has expired.
Credit balance too low
The prepaid credit has run out.
Add credit in the Console. Check why it ran out first.
429, or rate limited
Too many requests in a short time.
Usually a loop. Ask Claude why the job is making so many requests.
Model not found
The model name in the code is out of date.
Ask Claude to check the current model list in the documentation.
The app cannot read the response
The model returned prose where the code expected fields.
Make sure the request uses structured outputs.
The bill is higher than expected
Retries or a loop multiplied the requests.
Look at the run history in Inngest for repeated steps.
